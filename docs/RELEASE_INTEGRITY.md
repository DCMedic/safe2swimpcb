# Release identity and verification

A passing build, a GitHub Pages deployment, and a verified VPS response are three different claims. None establishes that collector observations are fresh or that a flag is safe for swimming.

## Build evidence

The Pages job deliberately checks out the latest `main` after a successful data workflow, because that workflow may have committed data after its triggering SHA. It captures `git rev-parse HEAD` immediately after checkout. `write_build_health.py` independently reads HEAD again and refuses to stamp a different SHA. `commit_sha` identifies the checkout; `trigger_sha` records `GITHUB_SHA` only as event context.

The job installs the repository requirements and actually runs JavaScript syntax checks, Python compilation/shell syntax, workflow and infrastructure validation, the full pytest suite, the HTML build, prerender consistency, and the repository health gate. Each marker validation value comes from its step's outcome. Missing or skipped results are `not_run`, failures are `failed`, and neither can become a passing build. The marker writer refuses publication if any required check did not pass. Both the writer and verifier require a full 40-character checkout SHA and positive workflow run ID and attempt; null or absent identities never compare as a successful release.

The source checkout will contain generated HTML after the build. The artifact inventory hashes those generated bytes, not just source files. Build evidence is workflow provenance, not a cryptographic signature or protection against a compromised runner.

## Public artifact boundary

`infra/public-artifact.json` is an exact, reviewed list of public paths, without wildcards. `scripts/stage_public_artifact.py` copies those files to a new directory outside the checkout in CI. It rejects missing files, symlinks, traversal, private directory paths and an existing output directory. New files are not automatically published. Add intended routes, assets or datasets to the allowlist in the same reviewed change that introduces them.

The allowlist retains public historical datasets, source context, workflow-health endpoints and publisher health. It excludes executable tooling, tests, infrastructure, repository metadata, internal documentation and `data/x_posting_state.json`. Staging derives content-addressed copies of allowlisted JavaScript, using the full SHA-256 in each filename, and rewrites every local HTML script reference to that exact generation. Static local JavaScript loader/import paths are recursively bound first, including the shared beach-navigation loader, before hashing their parent scripts. Unknown local scripts, dependency cycles and generated-name collisions fail closed. The original reviewed paths remain available for compatibility, but newly staged HTML never requests their unversioned JavaScript URLs. External CDN scripts are unchanged and are not covered by this generation binding.

These deterministic derived assets and the generated `data/site_build_health.json` are additional public artifact files. Their final bytes, including rewritten HTML and JavaScript, enter the build inventory. The workflow syntax-checks staged JavaScript after rewriting. This prevents a new page from combining a new safety controller with cached legacy renderer scripts under the documented stale-while-revalidate policy. It does not revoke already-open old documents or establish compatibility with an externally injected production guard. The test suite includes a deterministic old-browser-cache model; live browser/production-guard qualification remains separate.

The final local verifier requires an exact match between files in the artifact and its SHA-256 inventory. A missing, added or modified file fails verification. The allowlist governs source inputs; the final inventory also includes the deterministic fingerprinted JavaScript outputs. The upload action receives only this staged directory, never `.`.

## Target-specific checks

Before uploading an artifact or attempting any deployment, the job reads the Pages `base_url` with automatic enablement disabled and runs `--preflight`. The preflight requires an isolated Pages URL and rejects any nonempty staged `CNAME`. The repository currently contains `CNAME: knowthegulf.com`, so this branch intentionally blocks publication until the hosting/verification architecture is explicitly resolved. It does not publish first and report an inevitable verification failure afterward. Passing preflight only establishes configuration compatibility; it never claims that a release is live.

- `--target build` verifies the local inventory and validation evidence. Its result explicitly says deployment is not verified.
- `--target github-pages --url <configured Pages URL>` also requires the exact checkout SHA, workflow run, attempt and inventory at that URL; matching actual root-entry URL, `/index.html`, and all current flag/status JSON bytes; an isolated `https://dcmedic.github.io/safe2swimpcb/` origin, and the GitHub Pages HTTP server fingerprint. Custom-domain URLs remain unverified even if a response advertises that fingerprint. The URL comes from the successful deploy action, not a hard-coded assumption about the canonical domain.
- `--target vps --url <explicit VPS staging or production URL>` requires a build prepared with `--target vps`, matching release evidence and bytes, the security headers from `infra/policy.json`, and freshness-first cache policy. A Pages-targeted build cannot stand in as VPS verification.

Both serving-target checks use standard HTTPS certificate validation, cache-busting reads, and reject cross-origin redirects. VPS verification is scoped to the explicitly supplied HTTPS hostname; it does not independently establish ownership of an underlying machine. Verification results are printed to the job log; a generated build marker keeps `deployment.status: not_verified` because a file packaged before deployment cannot attest to that later operation. Target verification covers release identity, the homepage, and safety JSON; it is not a complete route, browser, DNS, certificate or network-origin audit. HTTP fingerprints are an additional fail-closed check, not cryptographic proof of hosting identity.

If the configured Pages URL uses the custom domain, redirects away from the isolated GitHub Pages origin, or serves through another intermediary, the Pages check fails rather than claiming that the VPS was deployed. Investigate the serving path. Do not weaken the check, redirect DNS, deploy to another host or change production monitoring merely to make it pass. Those actions require separate authorization.

## Local validation without publishing

Run the repository's validation commands and build transforms in an isolated checkout. The workflow documents their order. A focused test run is not a substitute for the full suite or the build gates. To test staging without writing build evidence:

```sh
python scripts/stage_public_artifact.py --output /tmp/ktg-public-review
```

Use a fresh output directory. The marker writer requires a real workflow run ID/attempt as well as explicit per-check workflow outcomes; running it locally without that identity and those outcomes intentionally refuses a passing release marker. Local staging and test results remain useful but are not workflow attestation. Never set success values for checks that were skipped or failed.

## Release and rollback decision

Review the exact branch SHA, full test results, generated artifact inventory and target-specific verification separately. Merging a branch, dispatching a workflow, publishing an artifact or switching a VPS release is a separate authorized action. This change does none of those by itself.

For any later authorized VPS rollout, validate a new release directory before an atomic switch. Keep the prior artifact and its build evidence so rollback can be verified against that prior release, not the failed new SHA. A healthy Pages build alone is not evidence that a VPS rollout or rollback succeeded.

The staged Caddy template includes no-store rules for current-status JSON and the build-health marker. These template changes are not applied to any running server by this branch.
